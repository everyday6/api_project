# NYC 내비게이션 세그먼트 지표 API — 설계 문서

- 날짜: 2026-08-21
- 상태: 브레인스토밍 완료, 사용자 검토 대기

## 1. 배경 / 목표

내비게이션이 사용하는 API를 만든다. NYC LION 도로망의 세그먼트별로 "빠른길(시간)"과 "최단거리(길이)" 두 지표를 미리 계산해두고, 내비게이션 클라이언트가 세그먼트 리스트를 주면 그 지표 값을 순서대로 돌려준다.

**최우선 원칙**: 신뢰성(정확성)보다 가용성이 우선이다. 파이프라인이나 일부 데이터가 장애 상태여도 API는 무조건 무언가를 응답해야 한다("무조건 응답").

## 2. 범위 (MVP)

- **포함**: type1(시간 = 길이/속도), type2(길이)
- **제외(향후 확장)**: type3(통행량) 등 — 이번 설계에서 구조적으로 확장 가능하게만 남겨두고 구현하지 않음
- **규모**: 뉴욕시 단일 도시, LION 세그먼트 약 10만 개 안팎

## 3. 입력 데이터

| 소스 | 제공 정보 | 갱신 주기 |
|---|---|---|
| LION (NYC 도로망) | segment_id, segment_length, 지오메트리 | 6개월 (LION 정식 릴리즈 주기) |
| [NYC DOT Traffic Speeds](https://data.cityofnewyork.us/Transportation/DOT-Traffic-Speeds/i4gi-tjb9) | 위경도(링크 포인트), 속도(SPEED), 타임스탬프(DATA_AS_OF) | 30분 |

`type1 = segment_length / speed` — 속도 데이터를 세그먼트에 매핑해서 계산.
`type2 = segment_length` — LION에서 그대로.

**단순화 가정**: 위 속도 데이터셋은 세그먼트별로 양방향/단방향 구분이 있을 수 있으나, 이번 설계에서는 그 구분을 무시하고 모든 세그먼트를 양방향으로 취급한다. `SPEED` 컬럼은 그대로 그 세그먼트의 평균속도로 가정해서 사용한다.

## 4. `time`의 의미

`time`은 특정 날짜의 실시간 스냅샷이 아니라 **하루 중 반복되는 시간대(time-of-day) 버킷**이다. 30분 단위로 하루 48개 버킷(`0000`~`2330`)을 두고, 각 버킷 값은 그 버킷이 갱신될 때 수집된 최대 6개(5분 간격 x 30분)의 원본 판독값을 **최신 판독값일수록 가중치를 높여(1:2:...:n 증가 가중) 평균**한 값이다. 여러 날에 걸친 과거 이력을 롤링 평균하지 않는다 — 매 갱신마다 그 버킷 하나만 완전히 새로 계산해서 덮어쓴다.

이 방식을 쓰는 이유: 내비게이션은 경로 상의 미래 시점(예: 지금부터 47분 후 도착 예정인 세그먼트)의 예상 소요시간이 필요한데, 시간대별 반복 패턴이면 미래 버킷도 바로 조회 가능하다. 실시간 스냅샷 방식이면 미래 시점 데이터가 존재하지 않는다.

## 5. 전체 아키텍처

```
[LION 파일]           [NYC 속도 피드]
     │                       │
     ▼ Bronze                ▼ Bronze
     (원본 그대로 S3에 적재)
     │                       │
     ▼ Silver1               ▼ Silver1
     (결측치 제거·컬럼 프루닝·컬럼명/타입 통일 — 데이터셋별로 개별 적용)
     └──────────┬────────────┘
                ▼ Silver2
                (조인: LION ↔ 속도데이터, 위경도 매핑)
                ▼ Gold1
                (필터링: 유효하지 않은 판독값 제외 등)
                ▼ Gold2
                (최종 산출물: 30분 버킷별 가중평균 + AVG)
                ▼
            DynamoDB (서빙 저장소, 계속 덮어써짐)
                             ▲
                    API (FastAPI, ECS Fargate
                    멀티 AZ + ALB)
                             ▲
                    [내비게이션 클라이언트]
```

파이프라인(Airflow+EMR)과 서빙(API+DynamoDB)은 완전히 분리된다. 파이프라인이 며칠간 죽어도 DynamoDB엔 마지막 성공 값이 남아있어서 API 가용성엔 영향이 없다.

### 파이프라인 단계 (Bronze → Silver1 → Silver2 → Gold1 → Gold2)

각 단계의 역할은 고정되어 있지만, **해당 데이터/타입에 그 작업이 필요 없으면 그 단계는 건너뛴다** (예: type2는 조인 대상이 없으므로 Silver2가 no-op).

| 단계 | 역할 | 저장 위치 |
|---|---|---|
| Bronze | 원본 그대로 적재 | S3 |
| Silver1 | 결측치 제거, 필요 컬럼 프루닝, 컬럼명 통일, 타입 통일 (데이터셋별 개별 적용) | S3/Parquet |
| Silver2 | 조인 (예: LION ↔ 속도데이터) — 조인 대상 없으면 스킵 | S3/Parquet |
| Gold1 | 필터링 (예: 유효하지 않은 판독값, 이상치 제외) | S3/Parquet |
| Gold2 | 최종 산출물 (API가 실제로 읽는 형태로 요약) | DynamoDB |

Silver1~Gold1은 무제한 누적되어도 저비용인 S3/Parquet에 두고, **Gold2만 DynamoDB에 올린다** — 세그먼트당 항목 수가 고정(버킷 수만큼)이라 크기가 무한히 늘지 않는다.

## 6. 서빙 저장소: DynamoDB (RDS 대신)

### 왜 DynamoDB인가

- 이 레이어의 접근 패턴은 순수 키 조회(`segment_id` + `type` + `time` → 값)뿐이다. 조인/집계는 이미 EMR/Spark가 끝냈으므로 관계형 DB의 강점(조인, 트랜잭션, 무결성 제약)이 서빙 단계에서는 쓰이지 않는다.
- **가용성이 구조적으로 다르다**: RDS(관계형 DB)는 항상 "쓰기를 담당하는 단일 노드"가 있어서, 그 노드가 죽으면 대기 노드를 승격(failover)하는 데 60~120초의 끊김이 발생한다. 이건 엔지니어링으로 없앨 수 없는 아키텍처적 한계다. DynamoDB는 여러 AZ에 항상 동시 복제되어 있어 "승격" 절차 자체가 없고, 그래서 이런 끊김이 없다.
- 팀에 RDS Multi-AZ/Proxy 같은 HA 구성 운영 경험이 없다는 점도 고려했다 — DynamoDB는 별도 HA 설정 없이 멀티 AZ가 기본이라 이 리스크가 없다.
- RDS의 강점(복잡한 쿼리, 분석 연계)은 이 서빙 레이어엔 불필요하다. 나중에 애드혹 분석이 필요해지면 Silver의 S3/Parquet 경로를 Athena로 조회하면 된다 — DynamoDB에 부담을 주지 않는다.

### 왜 타입별 별도 테이블인가

팀원들이 type별로 나눠서 파이프라인을 독립 개발한다. 단일 테이블 + 접두사 컨벤션(`TYPE#1#...`)도 가능하지만, 실수로 다른 타입 데이터를 건드릴 물리적 방지책이 없다. API 요청이 항상 "type 하나를 지정"해서 오는 구조라 "여러 타입을 한 번에 조회"하는 단일 테이블의 장점도 쓰이지 않는다. 따라서 **타입별 별도 테이블**로 간다.

### 스키마

**테이블 `SegmentMetricsType1`** (시간)

| segment_id (PK) | sk | value |
|---|---|---|
| 0077356 | `1200` | 30 |
| 0077356 | `1230` | 28 |
| 0077356 | `AVG` | 29 |
| GLOBAL | `DEFAULT` | 45 |

**테이블 `SegmentMetricsType2`** (길이)

| segment_id (PK) | sk | value |
|---|---|---|
| 0077356 | `LENGTH` | 500 |
| GLOBAL | `DEFAULT` | 300 |

type2는 시간에 따라 변하지 않으므로 버킷을 반복 저장하지 않고 세그먼트당 항목 1개만 유지한다.

## 7. Fallback 체인 ("무조건 응답")

API가 값을 조회할 때, **키가 없는 경우와 DynamoDB 호출 자체가 실패(에러/타임아웃)하는 경우 모두** 동일하게 다음 단계로 넘어간다:

1. 정확한 `(segment_id, bucket)` 값 — 이번 주기 갱신 실패해도 이전 성공 값이 그대로 남아있어 "최신값"과 "stale값"이 같은 읽기로 자연스럽게 처리됨
2. (type1만) `(segment_id, "AVG")` — 세그먼트 전체 시간 평균
3. `(GLOBAL, "DEFAULT")` — **파이프라인이 아니라 배포 시점에 수동으로 심어두는 고정값** (파이프라인이 한 번도 안 돌았어도 존재를 보장)
4. API 코드에 하드코딩된 상수 — 외부 호출이 전혀 없는 최후의 보루. DynamoDB 리전 자체가 완전히 응답 불가능한 극단적 상황에서도 이 단계는 항상 동작한다

추가로 API 서버 자체도 여러 AZ에 여러 인스턴스를 ALB 뒤에 띄워, 인스턴스 하나의 장애가 전체 서비스 장애로 이어지지 않게 한다.

*(참고: DynamoDB 전체 리전 장애처럼 극단적인 경우에 대한 멀티 리전 복제(Global Tables)는 현재 규모(뉴욕시 단일 도시)에는 과한 대응으로 판단해 이번 설계에서는 제외한다.)*

## 8. 파이프라인 (Airflow DAG)

**`segment_time_pipeline`** (30분 주기, type1)
0. NYC 속도 피드 API에 갱신된 데이터가 있는지 확인 (`DATA_AS_OF` 타임스탬프를 마지막 처리 시점과 비교) — 새 데이터 없으면 short-circuit으로 나머지 태스크 스킵
1. **Bronze**: 속도 피드 원본 수집 → S3 저장
2. EMR Serverless Spark job — 아래 단계를 수행:
   - **Silver1**: 속도데이터 결측치 제거·컬럼 프루닝(위경도/속도/타임스탬프)·컬럼명·타입 통일 (LION은 이미 별도로 정제된 최신 Silver1을 재사용)
   - **Silver2**: LION Silver1 ↔ 속도 Silver1 조인 (위경도 매핑)
   - **Gold1**: 유효하지 않은 판독값(속도 0 이하 등) 제외 필터링
   - **Gold2**: 그 버킷에서 수집된 원본 판독값(최대 6개)을 최신순 증가
     가중평균해서 30분 버킷 값 계산 — 여러 날 이력을 롤링하지 않고 매번
     그 버킷만 새로 계산해서 덮어씀 (+ 세그먼트 전체 평균 AVG, O(1) 증분 갱신)
3. Gold2 결과를 `SegmentMetricsType1`에 upsert
4. 실패 시 기존 Slack 알림 경로 재사용

**`segment_length_pipeline`** (6개월 주기 / LION 신규 파일 업로드 트리거, type2)
0. LION 데이터 포털에 새 릴리즈(버전/발행일)가 있는지 확인 — 없으면 short-circuit으로 스킵
1. **Bronze**: 신규 LION 파일 수집 → S3 저장
2. EMR Serverless Spark job:
   - **Silver1**: 결측치 제거·컬럼 프루닝(segment_id/length)·컬럼명·타입 통일
   - **Silver2**: 조인 대상이 없으므로 **스킵** (Silver1 결과를 그대로 사용)
   - **Gold1**: 길이가 0이거나 비정상인 세그먼트 제외 필터링
   - **Gold2**: 세그먼트당 길이 값 1개로 정리
3. Gold2 결과를 `SegmentMetricsType2`에 upsert

두 DAG 모두 0번 스텝은 Airflow의 short-circuit 패턴(예: `@task.short_circuit`)으로 구현 — 조건 미충족 시 이후 태스크 전체를 건너뛴다.

두 파이프라인은 서로 다른 스케줄·소스·EMR job·DynamoDB 테이블을 가지므로 완전히 독립적으로 개발 가능하다.

## 9. API 서비스

- FastAPI, ECS Fargate 멀티 AZ + ALB
- `POST /segments/values`
  - 요청: `{segment_ids: [...], type: 1 | 2, time: "12:00"}`
  - 응답: `{values: [...]}` (요청한 segment_ids 순서 그대로 보존)
- 로직:
  1. type에 따라 대상 테이블(`SegmentMetricsType1`/`SegmentMetricsType2`) 선택
  2. **type=2(길이)**: 시간과 무관 — `segment_ids`를 중복 제거해서 한 번에
     `BatchGetItem`(최대 100개, 초과 시 청크 분할)으로 조회 후 원래 순서/중복대로 복원
  3. **type=1(소요시간)**: `segment_ids`는 경로를 순서대로 나열한 것으로 간주한다.
     첫 세그먼트는 요청한 `time` 그대로 버킷(예: `12:03` → `1200`)을 조회하고,
     이후 세그먼트는 "앞 세그먼트들의 누적 소요시간만큼 시각을 이동"한 버킷을
     조회한다 — 그 세그먼트에 실제로 도착하는 시점의 값을 봐야 하기 때문이다.
     이 누적 시각은 앞 세그먼트의 조회 *결과*에 의존하므로 세그먼트를 순서대로
     하나씩 처리한다(배치 조회 불가). 같은 segment_id가 경로에 두 번 나와도
     등장 위치의 누적 시각이 다르면 값이 다를 수 있어 중복 제거를 하지 않는다.
  4. 누락/에러 항목은 7번 fallback 체인 순서로 채움 (type=1은 세그먼트별로
     자신의 누적 시각 기준으로 4단계를 통과시킨다)

## 10. 테스트 전략

- **단위 테스트**: `time = length/speed` 계산, 시간→버킷 변환, fallback 체인 로직(mock DynamoDB로 4단계 각각 검증)
- **통합 테스트**: 소규모 fixture로 Airflow DAG → EMR → S3(Silver) → DynamoDB(Gold) 전체 흐름 검증
- **API 테스트**: 정상 조회, 부분 누락, DynamoDB 전체 장애 케이스별 응답 검증 + 100개 초과 세그먼트 청크 분할 테스트

## 11. 향후 확장 (이번 범위 아님)

- type3(통행량) 추가 — 동일 패턴으로 `SegmentMetricsType3` 테이블 신설
- DynamoDB Global Tables를 통한 리전 이중화 (규모가 커지면 재검토)
- Silver(S3/Parquet) 데이터를 Athena로 연결한 애드혹 분석
