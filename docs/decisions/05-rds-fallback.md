# 05. 서빙 저장소 장애 대응을 위한 계층형 폴백

## 문제

- API가 RDS에만 의존해 조회 실패가 API 응답 품질 저하로 이어짐
- Type3 대량 적재 중 RDS 조회가 `statement_timeout`으로 반복 취소됨
- 25분 동안 40,528개 세그먼트 중 37,925개가 기본값으로 전환됨
- 기본값 폴백 비율이 최대 93.58%까지 증가함

## 원인

- 대량 적재 중 RDS 연결과 테이블 경합이 증가함
- RDS 장애 시 사용할 대체 데이터가 부족했음
- RDS를 계속 재시도하면 응답시간과 저장소 부하가 함께 증가함
- 바로 기본값을 반환하면 기존에 저장된 과거 데이터를 활용할 수 없음

## 대안

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| RDS 계속 재시도 | 최신값을 받을 가능성이 있음 | 응답이 느려지고 RDS 부하가 증가함 |
| 바로 기본값 반환 | 빠르고 단순함 | 사용할 수 있는 과거 데이터도 버림 |
| 계층형 폴백 | 가능한 데이터 중 더 신뢰할 수 있는 값을 사용 | 구현과 모니터링이 복잡함 |

## 결정

- RDS 응답이 느리거나 실패하면 빠르게 다음 저장소로 전환
- RDS 정상 조회 시 최신값과 과거 평균을 우선 사용
- RDS 장애 시 Lambda 메모리 캐시를 먼저 확인
- 메모리에도 없으면 S3 Gold 스냅샷 사용
- 모든 대체 데이터가 없으면 코드 기본값 반환
