# 04. [Type3] RDS 갱신 방식

## 문제
- 파티션별 직접 upsert → 너무 느림
- 스테이징 테이블 공유 → 파티션끼리 경합
- 병합 트랜잭션이 라이브 테이블 통째로 잠금 → 조회 실패 급증

## 원인
- upsert는 처리량 한계가 있어 동시성을 낮춰도 안 풀림
- 스테이징 테이블을 공유하면 "테이블 확장" 자체가 경합 자원이 됨
- 병합을 큰 트랜잭션 하나로 하면 조회 중인 라이브 테이블까지 잠김
- PK를 데이터 넣기 전에 만들면 삽입마다 인덱스 갱신 → 느려짐

## 대안

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| 파티션별 직접 upsert | 구현 단순 | 처리량 한계, 여전히 느림 |
| 공유 스테이징 + 단일 병합 | upsert보다 빠름 | 파티션 간 경합 |
| 파티션별 전용 스테이징 + upsert 병합 | 경합 없음 | 병합이 라이브 테이블 오래 잠금 |
| 파티션별 전용 스테이징 + PK 나중 생성 + 통째로 교체 | 경합 없음, 잠기는 시간 최소 | 디스크 일시적으로 두 배 사용 |

## 결정
- 파티션마다 각자 임시 테이블에 나눠 담기
- 다 담은 뒤에 PK 생성
- 완성된 결과로 기존 테이블을 통째로 교체
