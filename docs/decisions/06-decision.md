# 06. 변경 감지 마커는 운영 데이터 publish 성공 후 갱신한다

## 트리거

ETag로 원천 데이터의 변경을 감지할 때, 마커를 어느 시점에 갱신해야 하는지 결정해야 했습니다.

다운로드 직후 마커를 갱신하면 이후 Silver 변환이나 publish가 실패해도 해당 버전을 처리한 것으로 기록될 수 있습니다.

## 관측된 사실

- 파일 다운로드가 성공해도 이후 데이터 처리는 실패할 수 있습니다.
- 다운로드 직후 ETag를 갱신하면 실패한 파일도 처리 완료로 기록됩니다.
- 다음 실행에서는 변경이 없다고 판단해 해당 파일을 다시 처리하지 않습니다.
- 그 결과 운영 데이터가 이전 버전에 머물 수 있습니다.

## 근본 원인

하나의 ETag 마커를 원천 변경 감지와 처리 완료 확인에 함께 사용하면서, 마커 갱신 시점을 너무 이르게 설정한 것이 원인이었습니다.

따라서 마커는 새 버전을 발견한 시점이 아니라, 해당 버전이 운영 데이터에 정상적으로 반영된 시점을 나타내야 했습니다.


## 선택지

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| 다운로드 직후 갱신 | 중복 다운로드를 줄일 수 있음 | 후속 작업 실패 시 미처리 버전을 완료로 오인할 수 있음 |
| publish 성공 후 갱신 | 마커와 실제 운영 데이터 상태가 일치함 | 실패 시 동일 데이터를 다시 다운로드하고 처리할 수 있음 |

## 최적화 대상과 포기한 것

- **최적화 대상**: 처리되지 않은 원천 버전의 누락 방지와 실패 후 자동 재처리
- **포기한 것**: 실패 상황에서 발생할 수 있는 중복 다운로드와 추가 처리 비용

## 결정

ETag 마커는 다운로드나 Bronze 저장 직후가 아니라, **Silver 변환·검증과 운영 데이터 publish가 모두 성공한 후에만 갱신**하도록 했습니다.
