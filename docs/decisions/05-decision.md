# 05. 서빙 저장소 장애 시 계층형 폴백으로 응답한다

## 트리거

일부 세그먼트의 데이터가 없거나 RDS 조회가 실패해도, API 전체가 실패하지 않고 값을 반환할 방법이 필요했습니다.

## 관측된 사실

- 2026년 8월 25일 Type3 대량 적재 중 RDS 조회가 `statement_timeout`으로 반복 취소됐습니다.
- 19:05~19:30 KST에 Type3 RDS 조회 실패가 1,818건 발생했습니다.
- 같은 구간에 조회한 40,528개 세그먼트 중 37,925개가 코드 기본값으로 전환돼 기본값 폴백 비율이 **93.58%**까지 증가했습니다.
- 당시 RDS CPU는 평균 32.4%였지만 연결 수는 58개에서 최대 76개까지 증가했습니다.

## 근본 원인

API가 RDS에만 의존하면 RDS의 데이터 누락이나 장애가 API 장애로 이어집니다.

RDS를 계속 재시도하는 방법도 있지만, 장애가 지속되면 응답시간이 길어지고 RDS에 추가 부하를 줄 수 있습니다.

따라서 RDS를 사용할 수 없을 때 다른 데이터로 빠르게 전환하는 구조가 필요했습니다.

## 선택지

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| 바로 default값 반환 | 항상 빠르게 응답 가능 | 사용할 수 있는 과거 데이터도 버리게 됨 |
| 계층형 폴백 | 가능한 데이터 중 더 신뢰할 수 있는 값을 사용 | 구현과 모니터링이 복잡해짐 |

## 최적화 대상과 포기한 것

- **최적화 대상**: 데이터 누락이나 저장소 장애 상황에서도 API가 제한된 시간 안에 값을 반환하는 것
- **포기한 것**: 장애 상황에서도 항상 최신·정확한 값을 반환하는 것

## 결정

RDS 조회에 실패하거나 값이 없으면 오류를 반환하지 않고, **사용 가능한 대체값을 순서대로 찾아 반환**하도록 했습니다.

- **Type1**: 최신값 → 과거 평균 → 스냅샷 → 기본값
- **Type2·3·4**: RDS 값 → 스냅샷 → 기본값

이를 통해 일부 데이터가 없거나 RDS 장애가 발생해도 **API가 가능한 값을 반환하도록 했습니다.**
